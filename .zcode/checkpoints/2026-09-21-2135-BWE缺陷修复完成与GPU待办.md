## 7. 未决事项

1. **GPU/CUDA 改造未开始（原计划阶段 6–8，用户已选定「BWE + sherpa 降噪都上」）**。可行性已逐条查实：
   - BWE 三引擎：`audiosronnx` 的 API **本就有 `providers` 参数**，项目侧写死 CPU 的只有 `core/bwe.py` 一行 → 装 `onnxruntime-gpu` + 改一行 + 列表尾留 CPU 回退。
   - sherpa 六引擎：当前是 **CPU-only wheel**（无 `onnxruntime_providers_cuda.dll`，二进制内含「Please compile with `-DSHERPA_ONNX_ENABLE_GPU=ON`」）→ 必须换成 `+cuda12.cudnn9` 的 GPU wheel（约 200 MB，经由镜像站实测可达）。
   - DeepFilterNet3 的 `deep-filter.exe`：**永远上不了 GPU**（PE 导入表零 CUDA 依赖，推理栈是 Rust tract）。
   - 两个关键坑：`pip` 的 `onnxruntime-gpu` **对 sherpa 毫无帮助**（sherpa 用自带 DLL）；venv 里没有 cuDNN，而 conda base 的 torch 自带一套但被 `include-system-site-packages = false` 隔离，需显式让它可见。
   - 显存安全：`MAX_FRAMES_SINGLE_PASS = 72_000_000`（48 kHz 单声道约 690 MB）在 GPU 上会 OOM，必须调小，且 CPU/GPU 用同一个值（否则 device 会改变结果）。
2. **预设的「降噪强度」尚未按实测决定**。用户要求「适当测量后决定」。已知口径问题：`0` 的语义是**不设上限 = 压得最狠**，很容易被无意带进「识别用」场景；而三个预设**只有这一个处理参数不被触碰**。
3. **README 未写本轮修复**：4 个缺陷、`CHAIN_VERSION` 的用途与递增规则、以及必须更正的错误陈述「输出率 = 模型原生率」（实测为假：引擎上报 16000 但返回 48 kHz 数据）。
4. **`lavasr` 仍是最差引擎**，且这一点无法靠后处理修复：它自身对输出做 `np.clip(±1)`，生成段削顶的失真已烙进信号，降低电平救不回那一步。建议在 README 与界面上把它的默认地位进一步降级。

## 9. 补充说明

本轮修掉的 4 个缺陷是**叠加**的，且互相掩盖，单独看任何一个都不足以解释用户看到的现象：

| # | 缺陷 | 单独后果 | 为什么长期没被发现 |
|---|---|---|---|
| ① | BWE 循环把上一声道的**输出**率当成下一声道的**输入**率 | 第二路被误重采样（实测频谱上移 3 倍、长度变 1/3） | 第一路永远正确，所以表现为「一路正常一路坏」，不报错 |
| ② | 引擎**上报的输出率不可信**（sherpa 喂 48 kHz 上报 16000 却返回 48 kHz 数据） | 下游 BWE 拿了错的率，是①的上游根源 | README 与代码注释都写着「输出率 = 模型原生率」，这条错误认知被当成事实沿用了 |
| ③ | `align_to` 按**样本数**而非**时长**对齐 | 48 kHz 的扩展输出被截成 **1/3 时长**（静默数据丢失） | BWE 的断言只看频段内容、不看时长 |
| ④ | 三个 BWE 引擎**生成频段电平失控** | 听感「只剩高频」（lavasr 在 12–20 kHz 高 +89 dB 且自身已削顶） | 用「频段占比」判断会读反——相对占比被高得离谱的生成频段压到 1%，看起来像「低频被删了」；必须用**绝对**频段功率比才能定案 |

**一处方法论提醒（我在本轮踩过）**：判断「低频有没有被删」必须用**绝对**能量对比，不能用频段占比。我第一次用占比得出「低频被删」的结论是**错的**，后来改用绝对值才发现低频完好、真问题是高频太响。这条值得写进 README 的测量口径里。

**防复发机制**：本轮新增的三个守卫（`_stack` 长度差、`align_to` 补尾量、`CHAIN_VERSION`）不是装饰——`align_to` 的守卫在修复过程中**当场抓到了缺陷③**，而 `CHAIN_VERSION` 若不加，修复后应用会直接复用已经算坏的那份缓存（指纹只看参数、看不见代码缺陷）。

**用户数据完整性**：用户桌面两段真实录屏素材（约 18 min / 292 MB 与 5.3 min / 105 MB）全程只读，收尾复核 sha256 与 mtime 均未变。用户保留的坏产物**未删除**，作为对照证据（修复后产物因 `CHAIN_VERSION` 变化而指纹不同，两者可在变体列表里并排 A/B）。
